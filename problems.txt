Go has no covariant return types: Root() *RBTNode[T] does not satisfy an interface declaring Root() Node[T]. The signature must match exactly. So the only way to get both is to make the node type a parameter of the interfaces.

Option A — self-referential (F-bounded) generic interfaces

type Node[T cmp.Ordered, N any] interface {
	Value() T
	Count() int
	Parent() N
	Left() N
	Right() N
}

type Tree[T cmp.Ordered, N Node[T, N]] interface {
	Root() N
	Size() int
	Count(value T) int
	Insert(value T) error
	Delete(value T) error
}
*RBTNode[T] implements Node[T, *RBTNode[T]], and *RBT[T] implements Tree[T, *RBTNode[T]] while its methods return concrete types. Your line 8 assertion becomes var _ Tree[T, *RBTNode[T]] = &RBT[T]{}.

Shared algorithms then range over the node type:


func InOrder[T cmp.Ordered, N Node[T, N]](root N, visit func(N)) { ... }
Three things to know before committing:

The nil check gets awkward. Inside generic code you can't write n == nil, because N isn't known to be a pointer. You need var zero N; if n == zero, which requires N to be comparable — so you embed comparable in Node. The cost: an interface embedding comparable can only be used as a constraint, never as a type, so var n Node[int, ...] stops being legal. If you'd rather keep Node usable as a type, the alternative is an explicit IsNil() bool method on nodes, which is uglier but keeps both roles.

Every signature carries two type parameters, and inference doesn't always get there — expect occasional explicit instantiation like Values[int](tr). Generic type aliases (Go 1.24+, and you're on 1.26) hide it at use sites: type RBTree[T cmp.Ordered] = Tree[T, *RBTNode[T]].

BST needs the same treatment, with its own node type, or it won't share the algorithms.

Option B — two methods
Keep Root() Node[T] to satisfy the interface, add RootNode() *RBTNode[T] for concrete use. No design churn, works today, but you get a parallel API and callers must know which to reach for. Fine if the concrete return is a convenience rather than the point.

Option C — leave it alone
Worth saying plainly: interfaces already let you write shared algorithms — assertBSTProperty is one, and it works over BST and RBT equally. What Option A actually buys you is (a) concrete types at call sites without assertions, and (b) no interface boxing on every Left()/Right(), which for a hot traversal is a real allocation difference.

If your motivation is genuinely "define shared algorithms," you already have what you need and A is churn. If it's "shared algorithms and I don't want callers boxed into interfaces," A is the only real answer, and I'd take it with the comparable embedding.

I sketched these from the language rules rather than compiling them — if you want to go with A, I'd write it and verify it builds before you commit to the refactor.
